KeyboardLayout

Detects the OS keyboard layout and switches Enhanced Input mapping contexts automatically — no polling, no per-project C++.

Unreal Engine 5.8 · Windows (event-driven) · Enhanced Input integration

Overview

KeyboardLayout watches the keyboard layout of the OS window that has focus and reports it as a plain EKeyboardLayoutFamily enum value (QWERTY, AZERTY, QWERTZ, Dvorak, TurkishF). It deliberately doesn't expose the OS language: on Windows, the virtual-key codes for the Latin alphabet only move off QWERTY for layouts that actually rearrange it — AZERTY, QWERTZ's Y/Z swap, and the two layouts that rearrange everything (Dvorak, Turkish F) — while every other language (English, Spanish, Italian, Portuguese, Dutch, Polish, Turkish's default Q layout, and every non-Latin script, which keeps its Latin shortcuts pinned to the QWERTY positions) behaves exactly like QWERTY for gameplay bindings. So there are only ever a handful of families to map, not one entry per language. On Windows it reacts to the WM_INPUTLANGCHANGE system message, so detection is instant and costs nothing while the layout isn't changing — it never polls.

A per-player subsystem watches for layout changes and adds/removes the matching Input Mapping Context on the player's EnhancedInputLocalPlayerSubsystem automatically. Which context it picks for a given family can come from two places: a context your project authors once and KeyboardLayout translates automatically for every other family, or a context you hand-author yourself for full control. Both can be used together — see "Automatic key translation" below.

Setup

  1. Enable the KeyboardLayout plugin. It depends on Enhanced Input, which is enabled automatically.
  2. Open Project Settings → Game → Keyboard Layout.
  3. Set Canonical Mapping Context to the Input Mapping Context your project already authors with (the one with WASD on it). Leave Canonical Layout Family at its default, QWERTY.
  4. That's it for most projects: AZERTY and QWERTZ players now get a translated copy of that same context (ZQSD instead of WASD, etc.) with no second context to author or maintain.
  5. Only if you want bindings that aren't a mechanical translation of the canonical ones for a given family (or need Turkish F, which auto-translation doesn't cover yet — see below), add an entry for it in Layout Family Mappings instead; it takes priority over the automatic translation for that family.

Set Mapping Priority if these contexts need to outrank (or lose to) others already active. To give one specific player a different context instead, call SetContextForLayoutFamily on its KeyboardLayoutInputSubsystem — see the quick starts below.

Automatic key translation

KeyboardLayout can derive a working Input Mapping Context for AZERTY, QWERTZ and Dvorak from a single context you author in QWERTY, instead of requiring a hand-authored copy per family. It clones Canonical Mapping Context and swaps every key to its physical-position equivalent — e.g. W and A become Z and Q for AZERTY, the ZQSD convention — while every other property of the mapping (modifiers, triggers, the action it drives) is copied as-is. Keys outside that 26-letter block (digits, Space, mouse, gamepad, ...) are left untouched, since those already fire identically across every layout this plugin cares about.

Translation only runs between layouts with a verified table: QWERTY, AZERTY, QWERTZ and Dvorak. Turkish F isn't included — its full key-by-key layout hasn't been verified against real hardware, and guessing would be worse than leaving it alone. Give Turkish F a hand-authored context in Layout Family Mappings if you need to support it.

This complements, rather than replaces, hand-authored contexts: any family with an explicit entry in Layout Family Mappings uses that instead of the automatic translation, so you can mix both — translate by default, override the families that need something smarter than a mechanical key swap.

API reference

UKeyboardLayoutSubsystemEngine Subsystem

Owns detection and is the single source of truth for the current layout family. Exists for the lifetime of the engine.

OnKeyboardLayoutChangedEvent · (NewLayoutFamily: Keyboard Layout Family) — broadcast whenever the detected layout family changes.
GetCachedLayoutFamilyPure · returns Keyboard Layout Family — the last detected family, without re-querying the OS.
GetCachedLayoutIdPure, Advanced · returns String — the last detected raw platform layout id (Windows HKL as 8 hex digits). Only useful to tell apart layouts that share a family, e.g. France AZERTY vs. Belgian AZERTY.
UKeyboardLayoutBPLibraryBlueprint Function Library
GetCurrentKeyboardLayoutFamilyPure, static · returns Keyboard Layout Family — shortcut for UKeyboardLayoutSubsystem::GetCachedLayoutFamily, usable from any Blueprint without fetching the subsystem first.
GetCurrentKeyboardLayoutIdPure, static, Advanced · returns String — shortcut for GetCachedLayoutId.
EKeyboardLayoutFamilyEnum

Unknown, QWERTY, AZERTY, QWERTZ, Dvorak, TurkishF. On Windows, the virtual-key codes for the Latin alphabet only move off QWERTY for layouts that actually rearrange it:

AZERTYFrance, Belgium, Luxembourg, Monaco.
QWERTZY/Z swap only (never touches WASD): Germany, Austria, Swiss French/German, Czech, Slovak, Hungarian.
DvorakUS-Dvorak and its one-handed variants — a full rearrangement, unrelated to QWERTY. Still reports as the English language, so it's told apart by its own id, not by language.
TurkishFTurkish F ("F klavye") — a full rearrangement, distinct from the QWERTY-based Turkish Q most Turkish users actually have. Also told apart by id, not language.

Every other language — including every non-Latin script, which keeps its Latin shortcuts pinned to QWERTY positions — resolves to QWERTY. Recognizing another family is a one-line addition in the plugin's C++, no API change.

UKeyboardLayoutSettingsDeveloper Settings · Project Settings → Game → Keyboard Layout
Canonical Mapping ContextThe Input Mapping Context your project authors with. Any family with no entry in Layout Family Mappings gets an automatically key-translated copy of this one instead (see "Automatic key translation" above). Leave unset to disable auto-translation entirely.
Canonical Layout FamilyThe family Canonical Mapping Context was authored for. Default QWERTY; almost never needs changing.
Layout Family MappingsMap of Keyboard Layout Family → Input Mapping Context, for families that need something other than a mechanical translation of the canonical context (or that auto-translation doesn't cover, like Turkish F). Takes priority over auto-translation for any family listed here.
Mapping PriorityInt, default 0 — priority passed to AddMappingContext for every context above, auto-translated ones included.
Auto Apply To Local PlayersBool, default true — set to false to ignore Layout Family Mappings and Canonical Mapping Context, and only react to per-player overrides set via SetContextForLayoutFamily.
UKeyboardLayoutInputSubsystemLocal Player Subsystem

Applies the project's (or this player's own) layout family mappings to this player's Enhanced Input contexts. One instance per local player.

SetContextForLayoutFamilyCallable · (LayoutFamily: Keyboard Layout Family, Context: Input Mapping Context) — overrides, for this player only, which context that family gets, and re-applies immediately if it's the current one. Pass None as Context to make this player ignore that family.
ClearLayoutFamilyOverridesCallable · clears every override set via SetContextForLayoutFamily, falling back to Layout Family Mappings again.

Platform support

Detection is event-driven on Windows today. Detection lives behind a single internal interface, so support for another platform is a matter of adding one more implementation of it — nothing else in the plugin needs to change.
